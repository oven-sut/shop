## โดเมนที่ใช้ตอน login กลับ

```env
NEXT_PUBLIC_SITE_URL=https://www.neo.owenx.shop   # โปรดักชันเท่านั้น — ตอน dev ไม่ต้องตั้ง
```

ถ้าไม่ตั้ง ระบบจะใช้โดเมนของคำขอที่วิ่งเข้ามา ซึ่งถูกสำหรับ `next dev` และ preview
แต่พออยู่หลัง proxy เบราว์เซอร์อยู่โดเมนจริงส่วนแอปตอบอยู่โฮสต์ภายใน สองฝั่งจะไม่ตรงกัน

**ต้องตั้งใน Supabase ด้วย** ไม่งั้นแก้ที่โค้ดอย่างเดียวไม่พอ — Supabase จะปฏิเสธ
`redirectTo` ที่ไม่อยู่ในลิสต์แล้วเด้งไป Site URL แทนแบบเงียบ ๆ ซึ่งเป็นสาเหตุที่
login เสร็จแล้วไปโผล่ที่ `localhost:3000` ที่ Dashboard → Authentication → URL Configuration:

- **Site URL**: `https://www.neo.owenx.shop`
- **Redirect URLs**: `https://www.neo.owenx.shop/auth/callback` และ
  `http://localhost:3000/auth/callback` (เผื่อ dev)

ฝั่ง Google Cloud Console ไม่ต้องแก้ เพราะ redirect URI ของ OAuth ชี้ไปที่
`https://<project>.supabase.co/auth/v1/callback` ไม่ได้ชี้มาที่โดเมนร้าน

## ชั้นความปลอดภัย

ตัวคุมสิทธิ์จริงคือ RLS ในฐานข้อมูล ส่วนโค้ดฝั่ง route เป็นด่านที่สอง ตั้งใจให้ซ้ำกัน
เพราะสองด่านพังคนละแบบ — RLS ปฏิเสธ update จะหน้าตาเหมือน "ไม่มีแถวนี้" และ route
ที่ถูกเปลี่ยนไปใช้ service key เมื่อไหร่จะเหลือด่านเดียวโดยไม่มีใครรู้

| เรื่อง | อยู่ที่ |
| --- | --- |
| ตรวจ JWT ทุก request (cookie หรือ `Authorization: Bearer`) | `src/lib/api-auth.ts` |
| `requireAdmin()` สำหรับ route ที่แอดมินเท่านั้น | `src/lib/api-auth.ts` |
| ไม่คืนข้อความ error ดิบให้ client — log ไว้ฝั่งเซิร์ฟเวอร์แล้วคืนรหัสอ้างอิงแทน | `src/lib/api-response.ts` |
| จำกัดอัตราเรียกของ endpoint ที่เสียเงิน/โควตาจริง | `src/lib/rate-limit.ts` |
| Security headers (CSP, HSTS, X-Frame-Options, ฯลฯ) | `next.config.ts` |
| RLS policy + `revoke execute` ของฟังก์ชัน security definer | `supabase/schema.sql` |

**ข้อจำกัดที่ต้องรู้** — ตัวนับ rate limit เก็บในหน่วยความจำของโปรเซส รีเซ็ตทุกครั้งที่
deploy และถ้ารันหลาย instance แต่ละตัวจะนับแยกกัน มันมีไว้กันบัญชีเดียวยิงรัวจนโควตา
ผู้ให้บริการหมด ไม่ใช่เกราะกัน DDoS ถ้าย้ายไปรันหลาย instance ให้ย้ายตัวนับไปไว้ที่
Postgres หรือ Redis โดยแก้แค่ `hit()` ที่เดียว จุดเรียกใช้ไม่ต้องแก้

## หน้าติดต่อ (`/contact`)

ช่องทางติดต่อเก็บใน `store_settings` (`contact_line`, `contact_email`, `contact_phone`,
`contact_facebook`, `contact_hours`, `contact_note`) แก้ได้ที่หน้าแอดมิน → ตั้งค่าร้านค้า
ไม่ต้อง deploy ใหม่ · ช่องไหนเว้นว่างก็ไม่ถูกแสดง · รายการช่องอยู่ที่ `src/lib/contact.ts`
ที่เดียว ทั้งฟอร์มแอดมินและหน้าเว็บ map จากรายการเดียวกัน

หน้านี้**เปิดสาธารณะ** (คนยังไม่มีบัญชีก็ต้องติดต่อร้านได้) แต่ RLS ของ `store_settings`
ให้เฉพาะคนล็อกอินอ่าน และแถวเดียวกันมีเลขบัญชีร้านอยู่ด้วย — หน้านี้จึงอ่านด้วย service key
แล้ว **select เฉพาะคอลัมน์ `contact_*` ตามชื่อ** ไม่ใช่ `select('*')` เพื่อให้ต่อให้แก้หน้านี้
มั่ว ๆ ทีหลังก็ยังหลุดข้อมูลการเงินออกไปไม่ได้ (ทดสอบแล้วว่าเลขบัญชีไม่โผล่ใน HTML)

ค่าที่แอดมินกรอกจะกลายเป็นลิงก์ก็ต่อเมื่ออยู่ในรูปที่ปลอดภัยเท่านั้น — อีเมลต้องหน้าตา
เป็นอีเมล เบอร์ต้องมีตัวเลข ≥ 9 ตัว LINE/Facebook รับเฉพาะ `https://…` หรือไอดีที่เป็น
`[A-Za-z0-9._-]` นอกนั้นแสดงเป็นข้อความให้คัดลอกแทน (`javascript:` จึงไม่มีวันกลายเป็น href)

## คลังรหัส — ขายไอดี/คีย์ที่ร้านลงเอง

สินค้าที่ไม่ได้สั่งต่อจากซัพพลายเออร์ ขายจาก `public.product_codes` ได้ หนึ่งแถวคือของ
หนึ่งชิ้นที่ขายได้หนึ่งครั้ง เติมรหัสที่หน้าแอดมิน → แก้ไขสินค้า → คลังรหัสสำหรับขาย
วางได้ทีละหลายบรรทัด บรรทัดละหนึ่งชิ้น รูปแบบ `ชื่อผู้ใช้|รหัสผ่าน` หรือใส่รหัสอย่างเดียว

**ใส่รหัสซ้ำกันได้** — วางคีย์เดิมสิบบรรทัดคือมีของสิบชิ้นที่ขายได้สิบครั้ง เดิมมี unique index
`(product_id, code)` กันไว้และ API จะข้ามบรรทัดที่ซ้ำให้เงียบ ๆ ซึ่งผิดกับของที่ร้านขายจริง
อย่างคีย์ชุดเดียวที่ซื้อมาหลายสิทธิ์ ตอนนี้ดัชนีนั้นถูกถอดออกแล้ว การกันขายซ้ำยังอยู่ครบที่
`claimed_at` กับ `for update skip locked` ซึ่งเป็นตัวที่ทำหน้าที่นี้จริงมาตลอด

**สต็อกไม่ต้องกรอกเอง** — ทริกเกอร์ `product_codes_sync_stock` ตั้ง `products.stock`
ให้เท่ากับจำนวนรหัสที่ยังไม่ถูกขายทุกครั้งที่คลังเปลี่ยน ช่องสต็อกในหน้าแอดมินจึงถูกล็อก
เมื่อสินค้าชิ้นนั้นมีรหัสอยู่ ปล่อยให้กรอกทับได้เมื่อไหร่ สองตัวเลขนี้ก็ขัดกันเมื่อนั้น

**การจองรหัสอยู่ใน `place_order`** ทรานแซกชันเดียวกับที่ตัดเงินและตัดสต็อก ลูกค้าจึงไม่มี
ทางจ่ายแล้วไม่ได้รหัส และรหัสแถวเดียวขายซ้ำไม่ได้ (`for update skip locked` + `claimed_at`)
ถ้าจองได้ไม่ครบจำนวนที่สั่ง จะยกเลิกทั้งคำสั่งซื้อแทนที่จะส่งของขาด

### ขายได้ไม่จำกัด

เปิดสวิตช์ **"ขายได้ไม่จำกัด"** ในหน้าแก้ไขสินค้า (`products.is_unlimited`) สำหรับของที่
ส่งมอบซ้ำได้โดยไม่หมด — ลิงก์ดาวน์โหลด คีย์ที่ใช้ร่วมกันได้ รหัสส่วนลด

ลูกค้าทุกคนจะได้ **รหัสใบแรกในคลัง** ของสินค้าชิ้นนั้น โดยรหัสไม่ถูกตัดออก (`claimed_at`
ยังว่าง) ส่วนคอลัมน์ `stock` ของสินค้าแบบนี้ไม่มีความหมายและไม่มีอะไรไปแตะมันอีก:
`place_order` ไม่ตัด · `refund_order` ไม่คืน · `product_codes_sync_stock` ไม่เขียนทับ ·
หน้าร้านโชว์ "พร้อมส่งทันที" แทนจำนวน · แถบสถิติหน้าแรกไม่เอาไปรวมใน "จำนวนสินค้าที่เหลือ"

ยังไม่ได้ลงรหัสไว้เลยก็ขายได้ แต่ลูกค้าจะไม่ได้อะไรในหน้าประวัติการซื้อ (เหมือนสินค้าที่
คลังว่าง) — ลงรหัสไว้อย่างน้อยหนึ่งใบก่อนเปิดขาย

รหัสที่ขายแล้วเข้า `order_fulfillments` ด้วย `supplier = 'manual'` ลูกค้าจึงเห็นที่หน้า
**ประวัติการซื้อ** ที่เดียวกับไอดีจากซัพพลายเออร์ ต่างกันที่การ์ดแบบ manual ไม่มีปุ่มขอรหัส
Steam Guard เพราะไม่มีซัพพลายเออร์ให้ขอ ส่วน `refund_order` จะคืนรหัสเข้าคลังและลบแถว
ที่ส่งมอบทิ้ง ไม่งั้นลูกค้าจะยังเห็นรหัสที่ถูกเอาไปขายต่อให้คนอื่นแล้ว

ตรวจว่าทั้งหมดยังทำงานถูกได้ด้วย `node --env-file=.env scripts/verify-codes.mjs` — มันสร้าง
สินค้ากับรหัสจริงในฐานข้อมูล ไล่ทดสอบทริกเกอร์ การจอง และการคืนเงิน แล้ว rollback ทิ้งทั้งหมด

## จัดการผู้ใช้งาน — `/admin` → ผู้ใช้งาน

ค้นหาบัญชี (อีเมล ชื่อ หรือ user id) ดูยอดเงิน ยอดซื้อสะสม และครั้งล่าสุดที่เข้าใช้งาน
แล้วสั่งงานได้ 5 อย่าง: ตั้ง/ถอดสิทธิ์แอดมิน, ระงับ–ปลดระงับ, เพิ่ม–หักเงินในกระเป๋า,
สร้างบัญชีให้ และลบบัญชีถาวร รายละเอียดทั้งหมดอยู่ที่
[`docs/ARCHITECTURE.md` §12](docs/ARCHITECTURE.md)

สามข้อที่ทำให้ปวดหัวได้ถ้าไม่รู้ก่อน

- **แอดมินแตะบัญชีตัวเองไม่ได้** ทั้งปรับสิทธิ์ ระงับ และลบ — ถ้าถอดสิทธิ์ตัวเองสำเร็จ
  จะไม่เหลือทางกลับเข้าหลังบ้านเลย ต้องไปแก้ `raw_app_meta_data` ใน SQL Editor เอง
- **เปลี่ยนสิทธิ์แล้วยังไม่มีผลทันที** เพราะ role อยู่ใน JWT ของคนนั้น ไม่ใช่ตารางที่อ่านทุก
  รีเควสต์ — ต้องรอ token refresh รอบถัดไป (ไม่เกิน 1 ชั่วโมง) หรือให้เขาล็อกอินใหม่
  การระงับก็เหมือนกัน: กันล็อกอินครั้งต่อไป ไม่ได้เตะคนที่เปิดเว็บค้างไว้ออกทันที
- **ลบบัญชี = ลบประวัติทั้งสาย** ทุกตารางที่อ้าง `auth.users` ถูกตั้งเป็น `on delete cascade`
  คำสั่งซื้อของคนนั้นจึงหายจากรายงานยอดขายไปด้วย ถ้าแค่อยากห้ามเข้าใช้งานให้กด "ระงับ"

ปรับยอดเงินต้องพิมพ์เหตุผลกำกับ ระบบต่อท้ายอีเมลแอดมินที่กดให้เอง แล้วบันทึกลง
`wallet_transactions` เป็น `adjustment` ซึ่งลูกค้าเห็นในหน้ากระเป๋าเงินของตัวเอง

ต้อง **รันสคีมาใหม่หนึ่งรอบ** ก่อนใช้งาน (เพิ่มฟังก์ชัน `admin_list_users()` กับ
`admin_adjust_wallet()`) ตามหัวข้อถัดไป

## แดชบอร์ด — `/admin` → ภาพรวม

ตัวเลขทั้งหมดมาจาก `GET /api/stats/dashboard` ครั้งเดียว (แอดมินเท่านั้น) เพื่อให้ทุกตัวเลข
บนหน้าเป็นภาพ ณ วินาทีเดียวกัน — ยอดที่ขัดกันเองเพราะดึงคนละจังหวะแย่กว่าตัวเลขที่เก่าไปนิด
อ่านด้วย service key เพราะเป็นภาพรวมของทั้งร้าน ซึ่ง RLS ปิดไม่ให้ client เห็นข้ามคน

มีอะไรบ้าง: ยอดขายวันนี้/7 วัน/30 วัน/รวม · กราฟ 6 เดือนจากคำสั่งซื้อจริง · คำสั่งซื้อแยกสถานะ ·
**เงินคงเหลือในกระเป๋าลูกค้า (เป็นหนี้ของร้าน ไม่ใช่รายได้)** · เงินเติมแยกช่องทาง · ขายดี 5 อันดับ
(นับจาก `orders.items` ที่จ่ายแล้ว) · คลังรหัส · สต็อกต่ำ · ผู้ใช้ทั้งหมด · ความเคลื่อนไหวล่าสุด
จากบันทึกระบบ · สถานะไฟล์สำรองล่าสุด

ของเดิมวาดกราฟจากตัวเลขที่ฮาร์ดโค้ดไว้ในคอมโพเนนต์ พร้อมข้อความ "+18.4% จากเดือนที่แล้ว"
ที่ไม่มีข้อมูลรองรับ — แดชบอร์ดที่แต่งตัวเลขแย่กว่าไม่มีแดชบอร์ด เพราะมีคนเอาไปตัดสินใจ

## บันทึกระบบ (audit log)

ตาราง `audit_logs` เก็บว่า **ใครทำอะไรกับอะไร เมื่อไหร่** ดูได้ที่ `/admin` → บันทึกระบบ
(กรองตามกลุ่ม `topup.` `order.` `user.` `product.` `settings.` `backup.` และค้นข้อความได้)

| สิ่งที่บันทึก | action |
| --- | --- |
| เติมเงินทุกช่องทาง | `topup.slip` `topup.voucher` `topup.gateway` |
| แอดมินปรับยอดเงินลูกค้า | `user.wallet.adjust` |
| เปลี่ยนสิทธิ์/ระงับ/ลบบัญชี | `user.update` `user.delete` |
| เปลี่ยนสถานะคำสั่งซื้อ | `order.status` |
| เพิ่มสินค้า · แก้ตั้งค่าร้าน | `product.create` `settings.update` |
| สำรองข้อมูล | `backup.run` |

**เขียนด้วย service key เท่านั้น ไม่มี policy ให้ client เขียน แก้ หรือลบเลย** — log ที่คนถูกบันทึก
แก้เองได้ก็ไม่ใช่ log · อ่านได้เฉพาะแอดมิน (RLS) · หน้าเว็บก็มีแต่ปุ่มอ่านกับกรอง

`recordAudit()` (`src/lib/audit.ts`) **กลืน error ทุกกรณี** ตั้งใจให้เป็นแบบนั้น: คำสั่งซื้อต้อง
ไม่ล้มเพราะเขียน log ไม่ผ่าน บรรทัดที่หายยังตามจากข้อมูลจริงได้ แต่คำสั่งซื้อที่ล้มตามคืนไม่ได้
· `settings.update` เก็บ diff ว่าอะไรเปลี่ยนจากอะไรเป็นอะไร ไม่ใช่แค่ว่ามีคนกดบันทึก
· `user.delete` เก็บอีเมลไว้ด้วย เพราะทุกอย่างของบัญชีนั้น cascade หายไปหมดแล้ว

## สำรองข้อมูลอัตโนมัติ (ทุกวัน)

`GET|POST /api/cron/backup/<BACKUP_CRON_SECRET>` ดัมป์ทุกตารางของแอปเป็น JSON gzip
ก้อนเดียว อัปขึ้น Storage bucket **`backups` (private)** แล้วลบไฟล์ที่เก่ากว่า 14 วันทิ้งเอง
กดสำรองเดี๋ยวนี้ได้จากการ์ดในหน้าแดชบอร์ด (`POST /api/backups`) ซึ่งเรียกโค้ดตัวเดียวกัน

```env
BACKUP_CRON_SECRET=<สุ่มยาว ๆ>   # ไม่ตั้ง = endpoint ตอบ 404 ทุกครั้ง (fail closed)
```

ตั้งเวลาแบบไหนก็ได้ที่ยิง URL ได้วันละครั้ง:

```jsonc
// vercel.json — ถ้า deploy บน Vercel
{ "crons": [{ "path": "/api/cron/backup/<secret>", "schedule": "0 19 * * *" }] }
```
```bash
# หรือ crontab บนเซิร์ฟเวอร์ไหนก็ได้ (ตี 2 ตามเวลาไทย = 19:00 UTC)
0 19 * * * curl -fsS https://<โดเมนร้าน>/api/cron/backup/<secret> > /dev/null
```

**บอกตามตรงว่านี่คือ backup แบบไหน** — เป็นการสำรอง *ข้อมูล* (แถวในตาราง + รายชื่อบัญชี
id/อีเมล/สิทธิ์) ไม่ใช่ `pg_dump`: ไม่มีสคีมา ฟังก์ชัน policy หรือ trigger เพราะของพวกนั้นอยู่ใน
`supabase/schema.sql` ในกิตอยู่แล้ว และไม่มีรหัสผ่าน (GoTrue ไม่ให้ดึงออกมา)

กู้คืน = งานที่ต้องตั้งใจทำเอง: รัน `schema.sql` บนโปรเจกต์เปล่า → สร้างบัญชีกลับ → โหลดแถวเข้า
**ไม่มีปุ่ม restore อัตโนมัติโดยตั้งใจ** เพราะระบบที่ทับ production ได้เองคือระเบิดเวลา

ไฟล์สำรองคือทั้งร้านในไฟล์เดียว จึงอยู่ใน bucket private · ดาวน์โหลดได้เฉพาะแอดมินผ่านลิงก์
ที่เซ็นชื่อและหมดอายุใน 2 นาที · ตารางอ่านไม่ได้แม้แต่ตารางเดียว = ทั้งรอบล้มเลย ไม่ยอมอัปไฟล์
ที่ "ดูปกติแต่ว่างเปล่า" ขึ้นไป

## ซัพพลายเออร์ BYShop (แอปพรีเมียม)

ถอดสัญญามาจากตัวอย่าง PHP ที่ทางร้านเขาให้มา ทุกเส้นเป็น `x-www-form-urlencoded`
และ **ตอบ HTTP 200 เสมอแม้ตอนพลาด** — ความผิดพลาดอยู่ใน `{"status":"error","message":…}`
ของ body จึงห้ามเชื่อ `response.ok`

| เส้น | เมธอด | ต้องส่ง | ได้อะไร |
| --- | --- | --- | --- |
| `/api/product` | GET | — (ไม่ต้องมีคีย์) | สินค้า + สต็อก: `id, name, price, stock, status, category, img, product_info` |
| `/api/buy` | POST | `keyapi`, `id`, `username_customer` | บัญชีที่ซื้อได้ |
| `/api/history` | POST | `keyapi` (+`orderid` หรือ `username_customer`) | ประวัติ + email/password |
| `/api/report_fix` | POST | `keyapi`, `orderid`, `report_id` | แจ้งปัญหาออเดอร์ |

```env
SUPPLIER_BYSHOP_KEYAPI=<คีย์จากหน้า "เชื่อม API" ของ BYShop>
SUPPLIER_BYSHOP_BASE_URL=https://api_app_premium.byshop.me/api   # ไม่ต้องใส่ ยกเว้น endpoint ย้าย
```

ใช้งานที่ `/admin` → ซัพพลายเออร์ (อยู่ใต้ 499K Network) — เบราว์เซอร์ไม่เคยเห็น `keyapi`
ทุกอย่างวิ่งผ่าน `/api/supplier/byshop` ฝั่งเซิร์ฟเวอร์ · แคตาล็อกดูได้ตั้งแต่ยังไม่ตั้งคีย์
เพราะเส้นนั้นไม่ต้องยืนยันตัวตน · การสั่งซื้อกับแจ้งปัญหาเข้า audit log (`supplier.buy`,
`supplier.report`) เพราะทั้งสองอย่างใช้เครดิตและมีผลกับลูกค้า

**⚠️ การสั่งซื้อยังไม่ผูกกับการส่งของอัตโนมัติ** ตัวอย่างที่ได้มามีแค่ product/history/report_fix
ไม่มีของเส้นซื้อ สัญญาจึงยืนยันจากคำตอบจริงทีละฟิลด์ (ต้นทางบอกเองว่าขาดอะไร):

- `keyapi` — ยืนยันแล้ว (ตอบ "keyapi ไม่ถูกต้อง" ถ้าผิด)
- `username_customer` — ยืนยันแล้ว (ตอบ "กรุณาใส่ username_customer" ถ้าไม่ส่ง) คือ
  **ยูสเซอร์ลูกค้าฝั่ง BYShop** ที่เขาใช้กรองประวัติ กรอกได้ในหน้าแอดมิน เว้นว่าง = อีเมล
  แอดมินที่กด
- `id` — ยังไม่ยืนยัน ใช้ตามชื่อที่ `/api/product` ใช้ ถ้ายิงแล้วยังได้ "กรุณาใส่ …" อีก
  ชื่อในข้อความนั้นคือคำตอบ

หน้าแอดมิน **กางคำตอบดิบ** ของทุกครั้งที่กดให้ดู เอาไปยืนยันให้ครบก่อนค่อยต่อเข้า
`fulfillment.ts` ให้ส่งของอัตโนมัติเมื่อลูกค้าจ่าย

### นำสินค้าเข้าหน้าร้าน

ติ๊กเลือกในตารางแล้วกด **นำเข้าหน้าร้าน** — ราคาที่ BYShop ให้มาคือ *ต้นทุน* ของเรา จึงต้อง
บอกว่าจะบวกกำไรกี่ % (ค่าเริ่มต้น 20) ระบบคิดราคาขายแล้ว**ปัดขึ้นเป็นจำนวนเต็มบาท** เก็บ
ต้นทุนไว้ที่ `products.supplier_cost` ส่วนคำอธิบายถูกถอดแท็ก HTML ออกเป็นข้อความก่อนเก็บ
(ต้นทางส่ง HTML ดิบมา ถ้าเอาไปเรนเดอร์ตรง ๆ คือเปิดช่อง XSS ให้ต้นทาง)

กดนำเข้าซ้ำได้เรื่อย ๆ = **อัปเดตราคา/สต็อกของเดิม ไม่ใช่สร้างสินค้าซ้ำ** เพราะ upsert บนคู่
`(supplier, supplier_product_id)` เหมือนที่ 499K ใช้

### เปิด/ปิดการขายแอป

หน้าแอดมิน → ตั้งค่าร้านค้า → **ขายแอปจากซัพพลายเออร์** (`store_settings.sell_apps_enabled`)
ปิดแล้ว: สินค้าที่มี `supplier` หายจากหน้าร้าน และ **`place_order()` ปฏิเสธตั้งแต่ในฐานข้อมูล**
พร้อมบอกชื่อสินค้าที่ปิดขาย — ตะกร้าที่ค้างอยู่ในเบราว์เซอร์ยิงตรงมาได้เสมอ การซ่อนในหน้าร้าน
อย่างเดียวจึงไม่ใช่การปิด · ของที่ร้านลงเอง (`supplier is null`) ยังขายตามปกติ · แอดมินยังเห็น
สินค้าที่ปิดขายในหน้าจัดการ จะได้แก้ไขของพวกนั้นได้

ใช้ตอนต้นทางล่ม เครดิตหมด หรือยังไม่พร้อมขาย — ดีกว่ารับเงินลูกค้าแล้วส่งของไม่ได้

## รับข่าวสาร & โค้ดส่วนลด

ฟอร์มในฟุตเตอร์ทำงานจริงแล้ว (เดิม `preventDefault()` เฉย ๆ) — กดสมัครแล้วอีเมลลงตาราง
`newsletter_subscribers` ทันที

- **สมัครซ้ำได้ไม่เป็นไร** upsert บนอีเมลเสมอ จึงมีแถวเดียวต่อหนึ่งอีเมล ไม่งั้นตอนส่งจริง
  คนเดิมได้เมลสองฉบับ · เก็บเป็นตัวพิมพ์เล็กเสมอ ไม่งั้น `A@x.com` กับ `a@x.com` กลายเป็นสองคน
- **ยกเลิกแล้วไม่ลบแถวทิ้ง** ตั้ง `unsubscribed_at` แทน — เก็บไว้เป็นหลักฐานว่าเคยขอยกเลิก
  และมี `unsubscribe_token` สำหรับลิงก์ "ยกเลิกรับข่าว" ท้ายอีเมล (ยกเลิกได้โดยไม่ต้องล็อกอิน)
- **ตารางนี้ไม่มี RLS policy ให้ client เลย** เพราะข้างในคือรายชื่ออีเมลลูกค้าทั้งร้าน —
  ทุกอย่างผ่าน `/api/newsletter` ด้วย service key แล้วกรองสิทธิ์ที่นั่น: ใครก็สมัครได้
  แต่**อ่านรายชื่อได้เฉพาะแอดมิน**

หน้าแอดมิน → ตั้งค่าร้านค้า → **รับข่าวสาร & โค้ดส่วนลด**: ตั้งโค้ดต้อนรับ (โชว์ให้คนที่เพิ่ง
สมัคร — ต้องไปสร้างคูปองรหัสเดียวกันในหน้าคูปองด้วย ไม่งั้นใช้ตอนเช็คเอาต์ไม่ได้) และ
**ดาวน์โหลดรายชื่อเป็น CSV** (มี BOM ให้ Excel อ่านไทยออก และค่าที่ขึ้นต้นด้วย `=+-@`
ถูกนำหน้าด้วย `'` กัน CSV injection)

**ระบบยังไม่ส่งอีเมลเอง** — ยังไม่ได้ต่อผู้ให้บริการส่งเมล (Resend/SES/…) ตอนนี้จึงเป็นการ
*เก็บรายชื่อ* ให้เอา CSV ไปเข้าตัวส่งเมลที่ใช้อยู่ ถ้าจะให้ส่งเองบอกได้ ผมต่อให้ พร้อม
double opt-in (ยืนยันอีเมลก่อนนับเป็นสมาชิก) ซึ่งทำไม่ได้ถ้ายังส่งเมลไม่ได้

## รันสคีมาเข้า Supabase

```bash
# ใส่ DATABASE_URL ใน .env แล้วเรียก (รหัสผ่านจะได้ไม่ค้างใน shell history)
node --env-file=.env scripts/apply-schema.mjs
```

ทั้งไฟล์ถูกครอบด้วยทรานแซกชันเดียว ล้มตรงไหนคือฐานข้อมูลไม่ถูกแก้เลย และไฟล์เขียนแบบ
รันซ้ำได้ จึงรันกี่ครั้งก็ปลอดภัย

**host ต้องเป็น pooler ไม่ใช่ `db.<ref>.supabase.co`** — โฮสต์ตรงมีแต่ระเบียน AAAA (IPv6
ล้วน) เครื่องที่ไม่มีเน็ต IPv6 จะขึ้น `ENOTFOUND` ทั้งที่ชื่อโฮสต์ถูกแล้ว ให้ใช้ session pooler
ซึ่งมี IPv4 แทน สังเกตว่า username เปลี่ยนเป็น `postgres.<ref>` ด้วย:

```
postgresql://postgres.<ref>:<DB_PASSWORD>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

ต้องเป็นพอร์ต **5432** (session) ไม่ใช่ 6543 (transaction) เพราะ transaction mode รัน DDL
ยาว ๆ ในทรานแซกชันเดียวไม่ได้ ส่วน `<region>` ดูได้จาก `SUPABASE_S3_REGION` ใน `.env`

## ช่องทางรับเงินเติม

ตั้งได้พร้อมกันทุกช่องที่หน้าแอดมิน → ตั้งค่าร้านค้า กรอกช่องไหนก็เปิดช่องนั้น
ไม่กรอกเลยแม้แต่ช่องเดียว = เติมเงินไม่ได้ทั้งระบบ (กันคนเอาสลิปที่โอนให้คนอื่นมาเติม)

| ช่อง | คอลัมน์ใน `store_settings` | ทำอะไรได้ |
| --- | --- | --- |
| เลขบัญชีธนาคาร | `topup_receiver_account` | รับโอน + เทียบผู้รับในสลิป — สร้าง QR ไม่ได้ |
| พร้อมเพย์ | `topup_promptpay_id` | ทั้งเทียบสลิปและสร้าง QR ให้สแกน |
| ทรูวอลเล็ต | `topup_truemoney_phone` | รับซองอังเปา (เติมทันที) + เทียบสลิป |

ตอนตรวจสลิป ผู้รับในสลิปตรงกับ**ช่องใดช่องหนึ่ง**ก็ผ่าน — ลูกค้าที่สแกน QR กับลูกค้าที่โอน
เข้าเลขบัญชีถือสลิปของร้านเดียวกัน และตัวสลิปไม่ได้บอกว่าแอดมินกรอกเลขนั้นไว้ช่องไหน
**กติกาการเทียบ: เลขที่ธนาคารเปิดให้เห็น ต้องอยู่ในเลขที่ร้านตั้งไว้** ไม่ใช่เทียบ 4 ตัวท้าย
เพราะแต่ละธนาคารปิดคนละตำแหน่ง — กสิกร/MAKE โชว์ `xxx-x-x9947-x` คือเปิดหลักกลาง
แล้ว**ปิดหลักสุดท้าย** เทียบ 4 ตัวท้ายของเลขจริงจึงไม่มีวันเจอ ส่วนเจ้าที่คืนเลขเต็มมาก็ยัง
ผ่านเพราะเช็คอีกทางไว้ด้วย ผลพลอยได้คือ **เลขบัญชีในตั้งค่าต้องเป็นเลขเต็มและถูกต้อง**
พิมพ์ตกไปหลักเดียวสลิปจริงก็ถูกปฏิเสธหมด

เดิมมีช่องเดียว (`topup_receiver_account`) ที่ปนทั้งเลขบัญชีและพร้อมเพย์ — ตอน apply สคีมา
รอบแรกหลังอัปเดต ค่าเดิมที่เป็นพร้อมเพย์อยู่แล้วจะถูกย้ายเข้า `topup_promptpay_id` ให้เอง
ครั้งเดียว ไม่ใช่ทุกครั้งที่รัน ไม่งั้นพร้อมเพย์ที่แอดมินลบออกเองจะกลับมาทุกรอบ

## ซองอังเปาทรูมันนี่ (เติมทันที)

`POST /api/topups/truemoney` รับลิงก์ซอง (`gift.truemoney.com/campaign/?v=...`) ไปไถ่เข้า
เบอร์ทรูวอลเล็ตของร้าน แล้วเติมยอดที่ได้เข้ากระเป๋าลูกค้าทันที ไม่ต้องแนบสลิป
ซองใบเดิมใช้ซ้ำไม่ได้เพราะเก็บเป็น `trans_ref = truemoney:<hash>` ในตาราง `topups` เดียวกับสลิป
ซึ่ง unique อยู่แล้ว

**จุดที่ต่างจากสลิปโดยสิ้นเชิง: เงินย้ายก่อนแล้วค่อยตอบ** ไถ่แล้วคืนไม่ได้ ดังนั้น

- ยอดจากซอง**ไม่ถูกบังคับด้วย min/max** ของร้าน — ปฏิเสธหลังไถ่ = ยึดเงินลูกค้า
- อ่านยอดจาก `my_ticket.amount_baht` (ส่วนที่การไถ่ครั้งนี้ได้จริง) ไม่ใช่ยอดรวมของซอง
  ที่อาจถูกหลายคนแบ่งกัน
- error ทุกตัวถูกแยกว่า "ซองยังอยู่" หรือ "ซองถูกใช้แล้ว" — ถ้าไถ่สำเร็จแต่เขียน DB ไม่ผ่าน
  จะ log `[topup:truemoney] REDEEMED BUT NOT CREDITED` พร้อม user id/ยอด/ref ไว้ตามคืนมือ

### เจอ `truemoney_blocked` — endpoint ซองอังเปาปิดฝั่งเซิร์ฟเวอร์

**สถานะจริงที่ทดสอบแล้ว (ส.ค. 2569): ตัน** ลองยิงจากสามเครือข่ายที่ไม่เกี่ยวกันเลย —
เน็ตบ้าน, Cloudflare Worker, VPS คนละเจ้า — **403 หน้า HTML ของ Cloudflare ทั้งหมด**
(เน็ตบ้านผ่านช่วงสั้น ๆ ตอนเช้าแล้วโดนบล็อกหลังยิงถี่) เปลี่ยน User-Agent, ใช้ `node:https`
แทน `fetch`, หรือ curl ก็เหมือนกันหมด

**ทางที่ใช้ได้จริงคือรับทรูวอลเล็ตผ่านเกตเวย์** (`method: 'truemoney'` หัวข้อด้านบน) —
ทรูรับรอง ไม่ต้องมีรีเลย์ ไม่ชน bot protection ส่วนซองอังเปาให้ถือเป็นของแถมที่จะกลับมา
ใช้ได้ถ้าวันหลังเจอเครือข่ายที่ไม่โดนบล็อก

ถ้าอยากปิดช่องซองอังเปาไปเลย: ลบเบอร์ทรูวอลเล็ตออกจากหน้าแอดมิน ฟอร์มซองจะหายไปเอง

### ถ้ายังอยากลองรีเลย์

endpoint นี้เป็นตัวที่แอปทรูใช้เอง ไม่ใช่ API สาธารณะ และ `gift.truemoney.com` อยู่หลัง
bot protection ของ Cloudflare ซึ่ง**ให้คะแนน "ผู้เรียก" ไม่ใช่ตัวคำขอ** — วัดจากเครือข่าย
ที่ยิงมาและพฤติกรรมย้อนหลัง ไม่ใช่ header ที่ส่ง จึงเป็นได้ทั้งผ่านตอนแรกแล้วโดนบล็อกทีหลัง
และโดนบล็อกทุกครั้งตั้งแต่ต้นถ้าเป็น IP ของ VPS/คลาวด์ (แต่ง User-Agent ไม่ช่วยเลย
ทดสอบแล้วทั้ง Node fetch, node:https และ curl — พอ IP ติดบัญชีดำ โดนหมดทุกตัว)

กรณีนี้ถูกแยกเป็น `truemoney_blocked`: ลูกค้าเห็นแค่ว่า **ซองยังไม่ถูกใช้** (เพราะคำขอ
ไม่ได้ไปถึงระบบทรูเลย) ส่วนวิธีแก้ไปลง log ฝั่งเซิร์ฟเวอร์ ไม่ใช่หน้าจอลูกค้า

**วิธีแก้: ยิงผ่านรีเลย์** มีให้เลือกสองแบบ พฤติกรรมเหมือนกันเป๊ะ

| ไฟล์ | รันที่ไหน | เหมาะเมื่อ |
| --- | --- | --- |
| `docs/truemoney-proxy-worker.js` | Cloudflare Worker | ไม่มีเครื่องของตัวเอง / ไม่อยากดูแลอะไร — ออกเน็ตจากเครือข่ายของ Cloudflare เองจึงไม่โดนบล็อกแน่นอน |
| `docs/truemoney-proxy-server.mjs` | เซิร์ฟเวอร์ของตัวเอง (Node เปล่า ไม่มี dependency) | มีเครื่องที่ IP ไม่โดนบล็อกอยู่แล้ว |

**แบบรันเองมีข้อแม้ข้อเดียวแต่สำคัญ: IP ของเครื่องที่รันต้องไม่โดนบล็อก** — รันไว้บน
เครื่องเดียวกับร้านคือออกเน็ตด้วย IP เดิม โดนเหมือนเดิม ไม่ได้อะไรเลย เช็คก่อนด้วย
curl บนเครื่องนั้น (คำสั่งอยู่ในหัวไฟล์): ได้ 400/404 = ทรูตอบเอง ใช้ได้, ได้ 403 = โดนบล็อก

```bash
PROXY_SECRET=<สุ่มยาว ๆ> node docs/truemoney-proxy-server.mjs   # ค่าเริ่มต้น 127.0.0.1:8787
pm2 start docs/truemoney-proxy-server.mjs --name tm-relay && pm2 save
```

รับเฉพาะ `POST /campaign/vouchers/<hash>/redeem` เส้นเดียว นอกนั้น 404 หมด และถ้าเปิด
ออกอินเทอร์เน็ตต้องมี HTTPS ครอบ (nginx/Caddy) เพราะ secret วิ่งไปกับ header ทุกครั้ง
ตัวอย่าง systemd unit อยู่ท้ายไฟล์

```env
# ปกติไม่ต้องตั้ง — ใส่เมื่อ endpoint ย้าย หรือโดน Cloudflare บล็อก
TRUEMONEY_BASE_URL=https://<worker>.<subdomain>.workers.dev
TRUEMONEY_PROXY_SECRET=<ค่าเดียวกับ PROXY_SECRET ใน Worker>
```

`TRUEMONEY_PROXY_SECRET` ถูกส่งไปเป็น header `X-Proxy-Secret` และ Worker จะปฏิเสธ
ทุกคำขอที่ไม่มีมัน (รวมถึงตอนที่ยังไม่ได้ตั้ง secret เลย — fail closed) **รีเลย์ที่เปิดโล่ง
คือเครื่องมือให้ใครก็ได้ไถ่ซองคนอื่นเข้าเบอร์ตัวเอง** เพราะเบอร์ปลายทางมากับตัวคำขอ
ไม่ได้ฝังอยู่ในรีเลย์

ถ้ายังไม่อยากตั้งรีเลย์: ลองบนเซิร์ฟเวอร์ที่ deploy จริงก่อน บาง IP ก็ผ่านปกติ และการ
โดนบล็อกจากการยิงถี่ ๆ มักคลายเองเมื่อเว้นสักพัก — ปริมาณใช้งานจริง (ไถ่วันละไม่กี่ใบ)
แทบไม่ทำให้ติด

## ระบบตรวจสลิป (สำรองหลายเจ้า)

`/api/topups` ตรวจสลิปผ่าน `src/lib/slip` ซึ่งไล่ผู้ให้บริการทีละเจ้าจนกว่าจะมีเจ้าไหนตอบได้
ตั้งคีย์ของเจ้าไหนไว้ เจ้านั้นก็เข้าคิวเอง เจ้าที่ไม่ได้ตั้งคีย์จะถูกข้ามโดยไม่ยิงเน็ต

```env
# ลำดับที่จะลอง (ไม่ใส่ = ใช้ทุกเจ้าที่ตั้งคีย์ไว้)
SLIP_PROVIDERS=rdcw,slipok,thunder,easyslip

RDCW_CLIENT_ID=        # https://slip.rdcw.co.th
RDCW_CLIENT_SECRET=
RDCW_AMOUNT_UNIT=baht  # baht | satang

SLIPOK_BRANCH_ID=      # https://slipok.com
SLIPOK_API_KEY=

THUNDER_API_KEY=       # https://document.thunder.in.th/th/v2/

EASYSLIP_TOKEN=        # https://document.easyslip.com
```

ทุกเจ้ามี `*_BASE_URL` และ `*_AMOUNT_UNIT` ให้ override ได้ เผื่อผู้ให้บริการย้าย endpoint
หรือคืนยอดเป็นสตางค์

**กติกาการสลับเจ้า** — อยู่ที่ `SlipVerifyError.retryable`:

| สถานการณ์ | ทำอะไรต่อ |
| --- | --- |
| โควตาหมด / คีย์ผิด / แพ็กเกจหมดอายุ / โดน rate limit / เจ้านั้นล่ม (5xx) | ลองเจ้าถัดไป |
| อ่าน QR หรือยอดจากรูปไม่ออก | ลองเจ้าถัดไป (ตัวอ่านแต่ละเจ้าไม่เท่ากัน) |
| `NOT_FOUND` / `METHOD_NOT_ALLOWED` (ยิงผิด path หรือ endpoint ย้าย) | ลองเจ้าถัดไป |
| ธนาคารตอบว่าสลิปใบนี้ไม่ถูกต้อง (`SLIP_NOT_FOUND`, `VALIDATION_ERROR`) | **หยุดทันที** |

แถวที่สามเคยถูกจัดผิดเป็น "คำตัดสินของสลิป" ทั้งเส้นเลยหยุดตายที่เจ้านั้น ทั้งที่เจ้าถัดไป
ใช้ได้อยู่ — `NOT_FOUND` แปลว่า *ไม่มี route นี้* คนละเรื่องกับ `SLIP_NOT_FOUND`
ที่แปลว่าธนาคารไม่รู้จักสลิปใบนั้น

**Thunder กับ EasySlip อัปโหลดรูปที่ `POST {base}/verify/bank` เส้นเดียวกับ payload**
ฟิลด์ชื่อ `image` — ที่เอกสารแยกหน้าเป็น `/verify/bank/image` นั่นคือ path ของหน้าเอกสาร
ไม่ใช่ของ API ยิงตามนั้นได้ 404 `NOT_FOUND` เท่ากับ path มั่ว ๆ

ข้อสุดท้ายตั้งใจให้หยุด เพราะทุกเจ้าถามธนาคารกลางเดียวกัน ไล่ต่อไปก็ได้คำตอบเดิม
แต่เสียโควตาเจ้าอื่นฟรี ๆ ถ้าล้มครบทุกเจ้า ข้อความ error จะบอกว่าลองเจ้าไหนไปบ้าง
และติดรหัสอะไร เพื่อให้รู้ทันทีว่าต้องไปเติมโควตาเจ้าไหน

จะเพิ่มเจ้าใหม่ก็เขียนไฟล์ที่ทำตาม interface `SlipProvider` แล้วใส่ใน `ALL`
ที่ `src/lib/slip/index.ts` — ถ้าเจ้านั้นใช้ `Bearer` + `/verify/bank` แบบเดียวกับ
Thunder/EasySlip ใช้ `createBearerProvider()` ได้เลย ไม่ต้องเขียนใหม่

## 3 วิธีเติมเงินที่หน้ากระเป๋าเงิน

หน้ากระเป๋าเงินแยกเป็น 3 แท็บ ต่างกันที่ว่า **อะไรเป็นหลักฐานว่าเงินเข้าแล้ว**

| แท็บ | หลักฐาน | เข้าเมื่อไหร่ |
| --- | --- | --- |
| สลิปโอนเงิน | สลิปที่ตรวจกับธนาคารผ่าน `src/lib/slip` | หลังผู้ให้บริการยืนยันสลิป |
| QR | เกตเวย์รับชำระเงินแจ้งกลับมา (webhook) | อัตโนมัติ ไม่ต้องมีสลิป |
| ทรูวอลเล็ต | เกตเวย์แจ้งกลับมาหลังลูกค้ายืนยัน OTP · หรือคำตอบของทรูตอนไถ่ซองอังเปา | อัตโนมัติ / ทันทีที่ไถ่ซองผ่าน |

### เปิด/ปิดช่องทางได้จากหน้าแอดมิน

หน้าแอดมิน → ตั้งค่าร้านค้า → **ช่องทางเติมเงินที่เปิดรับ** มีสวิตช์ 4 ตัว
(`topup_slip_enabled`, `topup_qr_enabled`, `topup_truemoney_enabled`, `topup_voucher_enabled`
— default เปิดทั้งหมด) รายชื่อช่องกับข้อความอยู่ที่ `src/lib/topup-channels.ts` ที่เดียว
ทั้งฟอร์มแอดมิน หน้ากระเป๋าเงิน และ route handler อ่านจากรายการเดียวกัน

**ซ่อนแท็บไม่เท่ากับปิดช่อง** — ทุก endpoint เช็คสวิตช์ของตัวเองแล้วตอบ 503
`channel_disabled` เพราะเบราว์เซอร์ไม่ใช่ที่ตัดสินเรื่องนี้ (`/api/topups`,
`/api/topups/qr`, `/api/topups/charges`, `/api/topups/truemoney`)

**แต่รายการที่ลูกค้าจ่ายไปแล้วยังเข้าเงินตามปกติ** ปิดช่องคือหยุดรับ *รายการใหม่*
ไม่ใช่หยุด settlement — webhook กับการพอลลิงสถานะไม่เช็คสวิตช์เลย ไม่งั้นคนที่จ่ายแล้ว
จะเสียเงินฟรีเพราะแอดมินสับสวิตช์ระหว่างนั้น (ทดสอบไว้แล้ว)

ข้อควรระวังข้อเดียว: **ปิดช่องสลิปทำให้คนที่โอนเงินมาแล้วส่งสลิปไม่ได้** เพราะช่องนั้น
ลูกค้าโอนก่อนแล้วค่อยอัปโหลด ต่างจากช่องอื่นที่ยังไม่มีเงินขยับตอนกดปิด — ข้อความใน
หน้าแอดมินเตือนไว้ตรงสวิตช์แล้ว

แท็บ QR มีสองโหมด ขึ้นกับว่าตั้งคีย์เกตเวย์ไว้หรือยัง: **ตั้งไว้** = QR ที่จ่ายแล้วเงินเข้าเอง
(หัวข้อถัดไป) **ยังไม่ตั้ง** = QR พร้อมเพย์ที่ร้านวาดเอง ซึ่งยังต้องอัปสลิปที่แท็บแรก
เพราะไม่มีใครแจ้งกลับมาว่าเงินเข้า หน้าเว็บถามที่ `GET /api/topups/charges` ก่อนวาดแท็บ
เพื่อไม่สัญญาสิ่งที่ทำไม่ได้

## เกตเวย์ + webhook — QR และทรูวอลเล็ตที่เติมเงินให้เอง

ตั้งคีย์เกตเวย์แล้วได้สองช่องทางที่เงินเข้าเองโดยไม่ต้องมีสลิป ผ่าน endpoint เดียวกัน
`POST /api/topups/charges` (ต่างกันที่ `method`) แล้วเกตเวย์ยิง webhook กลับมาเมื่อจ่ายจริง

| `method` | ลูกค้าทำอะไร | ได้อะไรกลับไป |
| --- | --- | --- |
| `promptpay` (ค่าเริ่มต้น) | สแกน QR ในแอปธนาคาร | `qrPath` (รูป QR ที่ร้านส่งต่อให้) |
| `truemoney` | กรอกเบอร์ทรูวอลเล็ต**ของตัวเอง** แล้วยืนยัน OTP ที่หน้าผู้ให้บริการ | `authorizeUri` |

`truemoney` ตรงนี้คือทางที่ทรูรับรอง — เกตเวย์เป็นคนถือความสัมพันธ์กับทรู เราจึงไม่ต้อง
ยิง endpoint ที่ทรูไม่ได้เปิดให้เรียก (ดูหัวข้อซองอังเปาด้านล่างว่าทำไมทางนั้นถึงตัน)
เบอร์ที่กรอกเป็นของลูกค้าเอง ไม่เกี่ยวกับเบอร์รับเงินของร้าน และ `return_uri` ที่ส่งให้
เกตเวย์สร้างจาก `NEXT_PUBLIC_SITE_URL` เพราะต้องเป็นที่อยู่ที่เปิดได้จากมือถือลูกค้า
ไม่ใช่โฮสต์ที่คำขอนั้นบังเอิญวิ่งเข้ามา

```env
OMISE_SECRET_KEY=skey_...          # ตั้งอันนี้ = เปิดโหมดอัตโนมัติ
PAYMENT_GATEWAY=omise              # ไม่ใส่ = ใช้เจ้าแรกที่ตั้งคีย์ครบ
OMISE_BASE_URL=https://api.omise.co  # ไม่ต้องใส่ ยกเว้นจะยิงผ่านพร็อกซี/ตัวจำลอง
TOPUP_WEBHOOK_SECRET=<สุ่มยาว ๆ>    # ต่อท้าย URL ของ webhook
```

ตั้ง webhook ที่แดชบอร์ดของเกตเวย์เป็น
`https://<โดเมนร้าน>/api/topups/webhook/<TOPUP_WEBHOOK_SECRET>`

**กฎข้อเดียวที่ทั้งระบบยืนอยู่บนมัน: webhook เป็นแค่ "สัญญาณเตือน" ไม่ใช่หลักฐาน**
ใครก็ยิง JSON มาบอกว่าจ่ายแล้วได้ ตัว handler จึงอ่านจาก body แค่ *charge id* ตัวเดียว
แล้วไปถามยอด/สถานะ/เจ้าของกับ API ของเกตเวย์เองด้วย secret key ของร้าน — body ปลอม
จึงทำได้อย่างมากคือสั่งให้ร้านไปเช็ค charge จริงซ้ำ ส่วน secret ใน URL มีไว้กันคนแปลกหน้า
ยิงถี่ ๆ ให้ร้านเปลืองการเรียกเกตเวย์ ไม่ใช่ตัวที่ทำให้ปลอดภัย

`/api/topups/webhook` เป็น path เดียวใน `/api/*` ที่เปิดให้ไม่ต้องล็อกอิน (ดู `PUBLIC_PATHS`
ใน `src/proxy.ts`) เพราะเกตเวย์ไม่มีบัญชีในร้าน

รายละเอียดที่เหลือ:

- **เจ้าของรายการอยู่ใน `metadata.userId`** ของ charge ไม่ใช่ session — webhook ที่ไม่มี
  session จึงยังรู้ว่าจะเติมเข้าใคร และคนอื่นเปิดดู charge ของเราไม่ได้ (404)
- **หน้าเว็บพอลลิง `GET /api/topups/charges/[id]` ทุก 4 วิ แล้วเติมเงินได้เหมือนกัน**
  ตั้งใจให้ซ้ำกับ webhook: ถ้า webhook ตั้ง URL ผิดหรือเกตเวย์ล่ม ลูกค้าที่จ่ายแล้วต้องไม่
  ต้องมาเปิดเรื่องกับแอดมิน — ใครถึงก่อนได้ไป อีกทางกลายเป็น no-op เพราะ
  `unique(trans_ref)` ที่ `<gateway>:<charge_id>`
- **รูป QR ส่งผ่านร้าน** (`/api/topups/charges/[id]/qr`) ไม่ให้เบราว์เซอร์ยิงตรงไปโฮสต์
  ของเกตเวย์ และ URL ที่เกตเวย์ส่งมาถูกเช็คก่อนใช้ว่าเป็น https หรือโฮสต์เดียวกับ
  `OMISE_BASE_URL` เท่านั้น เพราะเราแนบคีย์ร้านไปกับการดึงรูปนั้น
- **min/max ถูกบังคับตอนเปิดรายการ** ต่างจากซองอังเปา เพราะยอดถูกล็อกก่อนลูกค้าจ่าย
- เติมเจ้าใหม่ได้โดยเขียนไฟล์ที่ทำตาม interface `PaymentGateway` แล้วใส่ใน `ALL`
  ที่ `src/lib/gateway/index.ts` — ต่างจากตัวตรวจสลิป ตรงนี้ไม่มีการไล่เจ้าถัดไป
  เพราะ charge อยู่ที่เกตเวย์เดียวและมีแค่เจ้านั้นที่ตอบได้ว่าจ่ายแล้วหรือยัง

## QR พร้อมเพย์ที่ร้านวาดเอง (ต้องมีสลิป)

`GET /api/topups/qr?amount=500` คืน payload มาตรฐาน EMV QRCPS กับรูป PNG (data URL)
ให้หน้า **กระเป๋าเงิน** เอาไปแสดง ลูกค้าสแกนจ่าย แล้วอัปโหลดสลิปต่อที่แท็บสลิป
— QR แบบนี้แค่ *ขอ* เงิน ไม่มีใครแจ้งกลับมาว่าเข้าแล้ว ตัวที่เติมเข้ากระเป๋าจริงจึงยังเป็น
การตรวจสลิปกับธนาคาร ไม่ต้องตั้งค่า env เพิ่ม ไม่ต้องต่อผู้ให้บริการเจ้าไหน

เลขที่เอาไปทำ QR มาจาก `store_settings.topup_promptpay_id` เท่านั้น (ถ้าว่างจะลองอ่าน
`topup_receiver_account` เผื่อแอดมินยังกรอกพร้อมเพย์ไว้ช่องเก่า) ไม่รับจาก query
เพราะไม่งั้นใครก็แจก QR ที่เงินเข้าบัญชีตัวเองในนามร้านได้ และยอดต้องอยู่ในช่วง
min/max เดียวกับที่ตอนตรวจสลิปใช้ — ออก QR ยอดที่เดี๋ยวจะถูกปฏิเสธ คือเก็บเงินลูกค้าก่อน
แล้วค่อยบอกว่าใช้ไม่ได้

**พร้อมเพย์รับได้ 3 แบบเท่านั้น** — เบอร์มือถือ 10 หลัก, เลขบัตรประชาชน/ผู้เสียภาษี 13 หลัก,
e-Wallet 15 หลัก (`readPromptPayTarget()` ที่ `src/lib/promptpay-id.ts`) เลขบัญชีธนาคารเฉย ๆ
ทำ QR ไม่ได้ ต้องเช็คเองเพราะ `promptpay-qr` ไม่เคยปฏิเสธ: มันเติม 0 ข้างหน้าให้ครบ 13 หลัก
แล้วคืน QR ที่สแกนได้แต่ไม่มีปลายทาง หน้าแอดมินจึงบอกใต้ช่องกรอกเลยว่าเลขที่ใส่อยู่
ทำ QR ได้หรือไม่ และหน้ากระเป๋าเงินจะซ่อนปุ่มสร้าง QR ไปเลยถ้าทำไม่ได้

ตัวเข้ารหัส (`promptpay-qr` + `qrcode`) อยู่ใน `src/lib/promptpay.ts` ซึ่งเรียกจากฝั่ง
เซิร์ฟเวอร์เท่านั้น ส่วนกฎว่าเลขแบบไหนใช้ได้แยกไว้ที่ `promptpay-id.ts` ให้ฝั่งเบราว์เซอร์
import ได้โดยไม่ลากสองไลบรารีนั้นไปด้วย
